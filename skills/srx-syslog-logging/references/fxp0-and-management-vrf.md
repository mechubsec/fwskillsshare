Background for the logging skill. Junos treats the control plane (Routing Engine,
fxp0) and the data plane (PFE, revenue ports) as separate paths, and the rules
differ by what you are sending and where. Most confusion in this area comes from
applying a rule from one plane to the other.

**Verify platform and release support** in Juniper Feature Explorer or the
documentation for your exact model before relying on any behaviour here. Support
for fxp0 in a management routing instance in particular has varied across
platforms and releases.

## What fxp0 is

fxp0 is a dedicated out-of-band management interface attached to the Routing
Engine. It is **not** part of the packet forwarding engine, so no flow or
security processing happens on it — it needs no security zone and no security
policy, and traffic on it is not subject to policy lookup.

It comes up before the forwarding plane, which is why it is the conventional
interface for initial access and zero-touch provisioning.

On a chassis cluster, each node keeps its own fxp0 address — they are not synced
— so nodes remain independently reachable during failover. A `backup-router`
statement gives the standby node a path out before the routing protocol daemon is
running.

## Should fxp0 go in a management routing instance?

By default fxp0 shares `inet.0` with production and control traffic. Putting it in
a dedicated management instance (commonly `mgmt_junos`) gives management its own
routing table.

**Reasons to do it**

- Management routing is isolated from the dataplane table, so management traffic
  cannot be reached via, or leak into, production routing.
- Troubleshooting becomes more deterministic — there is one table for management
  and one for transit.
- A dedicated management instance is widely recommended as good practice for
  device management separation.

**Reasons to be careful**

- The non-default management instance supports only the management interface
  (em0/fxp0). It is not a general-purpose management-segmentation tool and cannot
  be extended to other interfaces.
- Support has historically been inconsistent across SRX platforms and releases.
  On some, the statement is rejected outright with *"Referenced routing instance
  must be defined under [edit routing-instances]"*.
- **Every** service that uses fxp0 must then specify the routing instance —
  syslog, NTP, DNS, RADIUS, JIMS, and anything else. Miss one and it silently
  fails to route while looking correctly configured. This is the most common way
  the feature bites people.
- It adds a second routing table to remember during troubleshooting. On a small
  lab or test device where isolation is not a real requirement, the friction may
  outweigh the benefit.

## Why Security Director Cloud requires a revenue interface

This follows from how SRX security logging works rather than being an arbitrary
requirement.

In `mode stream`, security logs are generated and sent **by the PFE**, directly
out a revenue port to the collector, bypassing the Routing Engine. fxp0 is not
part of the PFE, so it structurally cannot carry stream-mode security logs —
regardless of whether fxp0 sits in the default instance or a management instance.

Security Director Cloud therefore requires a production/transit interface with a
routable address, both for that telemetry path and for management connectivity.

## Which source for which log type

| Log type | Recommended source | Why |
|---|---|---|
| System / control-plane (`set system syslog`) | fxp0, or a management instance | Low volume, generated by the RE itself, no PFE involvement |
| Security / traffic, `mode stream` or `stream-event` | Revenue port — **not** fxp0, via `set security log source-interface` or `source-address` | Stream mode is PFE-generated; fxp0 is not on the PFE |
| Security / traffic, `mode event` | The **system syslog** path — configure `set system syslog`, which may use fxp0 | The RE processes the logs, so delivery follows the control-plane path |

Note the asymmetry, because it catches people out: `set security log
source-interface` **never** accepts fxp0, whatever `mode` is configured. Junos
rejects it at commit with `This interface cannot be configured for log, only
revenue port is allowed` — measured on SRX345 (26.2R1.7) and vSRX (24.4R1.9)
with `mode event` set in the same candidate. Juniper's CLI reference scopes the
prohibition to stream mode, so the CLI is stricter than the documentation.

That is not a contradiction once you see the two are different knobs. In
`mode event` you do not point `security log source-interface` anywhere — the
Routing Engine hands the logs to the system syslog path, and
`set system syslog source-address` is what selects the source there.

On larger chassis SRX platforms the separation matters more, because the RE and
PFE are on physically separate boards. Forcing security logs through the RE in
event mode means every log crosses the backplane, and at high log rates that can
saturate the control plane. Branch platforms are more tolerant, and stream mode
is the usual default there.

## Do and don't

**Do**

- Use fxp0 for out-of-band access — SSH, HTTPS, NETCONF. Never bind a security
  zone or policy to it.
- Consider a management routing instance where the platform and release support
  it and you want genuine routing isolation.
- Give each cluster node a unique fxp0 address plus a `backup-router` statement.
- Configure a revenue interface with a routable address for SD Cloud onboarding
  and for streaming security logs.
- Send security logs with `set security log mode stream` sourced from a revenue
  port, with a route to the collector through that port.
- Add the routing-instance qualifier to every fxp0-dependent service once a
  management instance is in use.

**Don't**

- Don't source stream-mode security logs from fxp0 — it cannot work, and SD Cloud
  will not configure it.
- Don't address fxp0 into a dataplane subnet, or route between the management and
  dataplane tables. Keep fxp0 on its own logical network; Junos will not install
  cross-routes, and the symptom is a change that appears to be ignored rather
  than to fail.
- Don't rely on event-mode security logging through the RE at scale on chassis
  platforms.
- Don't forget the routing-instance qualifier anywhere once the management
  instance is enabled — the failure is silent.
